HELM COMMANDS — CLIMBING MANAGEMENT
====================================


INSTALL HELM
------------

# Install Helm using Chocolatey.

choco install kubernetes-helm


# Check that Helm is installed and see the installed version.

helm version



HELM CHART STRUCTURE
--------------------

# Our Helm chart is located here:

helm/
└── climbing-management/
    ├── Chart.yaml
    ├── values-dev.yaml
    ├── values-prod.yaml
    └── templates/
        ├── deployment.yaml
        └── service.yaml


# Chart.yaml
# ----------
# Contains metadata about the Helm chart.
#
# Example:
#
# apiVersion: v2
# name: climbing-management
# version: 0.1.0
# appVersion: "1.0.0"


# values-dev.yaml / values-prod.yaml
# -----------------------------------
# Contain environment-specific configuration.
#
# For example:
#
# DEV:
#   replicaCount: 1
#   image:
#     tag: "<commit-sha>"
#
# PROD:
#   replicaCount: 2
#   image:
#     tag: "<commit-sha>"


# templates/
# ----------
# Contains Kubernetes YAML templates.
#
# Helm replaces expressions such as:
#
#   {{ .Values.replicaCount }}
#   {{ .Values.image.repository }}
#   {{ .Release.Name }}
#
# with real values before sending the resulting Kubernetes manifests
# to the Kubernetes API.



CHART VALIDATION
----------------

# Render the Helm chart locally.
#
# This does NOT deploy anything to Kubernetes.
#
# It takes:
#
#   Chart + templates + values
#
# and shows the final Kubernetes YAML that Helm would generate.

helm template climbing-dev ./helm/climbing-management `
-f ./helm/climbing-management/values-dev.yaml


# Validate the Helm chart.
#
# Helm checks for structural and configuration problems such as:
#
# - Is Chart.yaml valid?
# - Are the templates syntactically correct?
# - Are required chart fields present?
# - Are there obvious configuration problems?
#
# IMPORTANT:
# Our project does not have a values.yaml.
# Therefore, specify the environment values file explicitly.

helm lint ./helm/climbing-management `
-f ./helm/climbing-management/values-dev.yaml



HELM RELEASES
-------------

# A Helm RELEASE is a specific installation of a Helm chart.
#
# The same chart can create multiple independent releases.
#
# In our project:
#
#   climbing-dev
#       = DEV release
#
#   climbing-prod
#       = PROD release
#
# Both releases use the same Helm chart but different values files.


# Install a new DEV release.

helm install climbing-dev ./helm/climbing-management `
-f ./helm/climbing-management/values-dev.yaml


# Install a new PROD release.

helm install climbing-prod ./helm/climbing-management `
-f ./helm/climbing-management/values-prod.yaml


# IMPORTANT:
#
# "helm install" is for creating a NEW release.
#
# If the release already exists, use:
#
#   helm upgrade
#
# instead.



UPGRADE A RELEASE
-----------------

# Upgrade the existing DEV release.
#
# Helm compares the current release with the new chart configuration
# and updates the Kubernetes resources when necessary.

helm upgrade climbing-dev ./helm/climbing-management `
-f ./helm/climbing-management/values-dev.yaml


# Upgrade the existing PROD release.

helm upgrade climbing-prod ./helm/climbing-management `
-f ./helm/climbing-management/values-prod.yaml


# A useful alternative is:
#
#   helm upgrade --install
#
# This means:
#
#   "Upgrade the release if it exists,
#    otherwise install it."
#
# This is commonly used in CI/CD pipelines.

helm upgrade --install climbing-dev ./helm/climbing-management `
-f ./helm/climbing-management/values-dev.yaml



LIST HELM RELEASES
------------------

# Show the Helm releases installed in the current Kubernetes context.

helm list


# Example:
#
# NAME             NAMESPACE    STATUS
# climbing-dev     default      deployed
# climbing-prod    default      deployed



CHECK RELEASE STATUS
--------------------

# Show detailed information about a Helm release.

helm status climbing-dev


# Show the complete revision history of a release.

helm history climbing-dev


# Every helm upgrade creates a new revision.
#
# Example:
#
# REVISION    STATUS
# 1           superseded
# 2           superseded
# 3           deployed
#
# The revision number belongs to the Helm release.
#
# It is NOT the Docker image version.
# It is NOT the Git commit SHA.



VIEW RELEASE VALUES
-------------------

# Show the values explicitly configured for the release.

helm get values climbing-dev


# Show all values used by the release, including default values
# and values inherited from the chart.

helm get values climbing-dev -a


# This is useful when debugging:
#
# "What configuration did Helm actually use?"



VIEW GENERATED KUBERNETES MANIFESTS
-----------------------------------

# Show the Kubernetes YAML generated by Helm
# for the current release.

helm get manifest climbing-dev


# This is useful when you want to understand:
#
# Chart templates
#       +
# Values
#       =
# Final Kubernetes YAML
#
# You can then compare the generated YAML with:
#
# kubectl get deployment ... -o yaml



ROLLBACK
--------

# Roll back a Helm release to a previous revision.

helm rollback climbing-dev 4


# This means:
#
# "Restore the configuration represented by Helm revision 4."
#
# Helm creates a NEW revision for the rollback.
#
# It does not simply delete the newer revisions.
#
# After rollback, check:
#
helm history climbing-dev


# Then verify the Kubernetes rollout:

kubectl rollout status deployment climbing-dev-climbing-management



KUBERNETES ROLLOUT
------------------

# Restart all Pods belonging to the Deployment.

kubectl rollout restart deployment climbing-dev-climbing-management


# Watch until the new Pods are successfully deployed.

kubectl rollout status deployment climbing-dev-climbing-management


# Show the current Pods.

kubectl get pods


# Watch Pods change in real time.

kubectl get pods -w


# Useful when Kubernetes is replacing old Pods with new Pods.

VERIFY THE DOCKER IMAGE
-----------------------

# Show the Docker image configured in the Pod.

kubectl get pod climbing-dev-climbing-management-d7c7bcf6d-r7drp `
-o jsonpath="{.spec.containers[0].image}"


# Example:
#
# ghcr.io/rmarintech/climbing-management-sb:85126b7130d8493d8e0212e416599968c33290a1


# The tag tells us which image tag Kubernetes was configured to use.
#
# In our deployment we use the Git commit SHA:
#
#   :85126b7130d8493d8e0212e416599968c33290a1
#
# This gives us an immutable application version identifier.


# Show the exact image ID/digest actually running in the container.

kubectl get pod climbing-dev-climbing-management-d7c7bcf6d-r7drp `
-o jsonpath="{.status.containerStatuses[0].imageID}"


# The imageID contains the SHA256 digest of the actual image.
#
# This is even more precise than the Docker tag.
#
# Tag:
#
#   :85126b7...
#
# Digest:
#
#   @sha256:d671c...
#
# The digest identifies the exact image content.



IMPORTANT: HELM + DOCKER VERSIONING
-----------------------------------

# Docker image tags can be mutable.
#
# Example:
#
#   latest
#
# can point to a different image tomorrow.


# Our CI pipeline creates two tags:

latest

<git-commit-sha>


# Example:

ghcr.io/rmarintech/climbing-management-sb:latest

ghcr.io/rmarintech/climbing-management-sb:85126b7130d8493d8e0212e416599968c33290a1


# "latest" is convenient for development,
# but it is not ideal for production deployments.
#
# The Git commit SHA gives us a reproducible version:
#
# Git commit
#     |
#     v
# Docker image
#     |
#     v
# GHCR
#     |
#     v
# Helm
#     |
#     v
# Kubernetes
#
# Therefore we know exactly which application version
# is deployed to Kubernetes.



IMPORTANT HELM CONCEPTS
-----------------------

# CHART
#
# A Helm chart is a package containing:
#
# - Chart.yaml
# - values files
# - Kubernetes templates
#
# It describes HOW an application should be deployed.


# RELEASE
#
# A release is one specific installation of a chart.
#
# Example:
#
#   climbing-dev
#
# is one release.
#
#   climbing-prod
#
# is another release.


# VALUES
#
# Values provide configuration to the chart.
#
# Example:
#
#   .Values.replicaCount
#   .Values.image.repository
#   .Values.image.tag
#   .Values.service.port
#
# values-dev.yaml and values-prod.yaml allow the same chart
# to be configured differently for each environment.


# TEMPLATES
#
# Templates contain Kubernetes YAML with Helm expressions.
#
# Example:
#
#   replicas: {{ .Values.replicaCount }}
#
# Helm replaces the expression with the value from the selected
# values file.


# RELEASE NAME
#
# .Release.Name comes from the Helm release.
#
# Example:
#
# helm install climbing-dev ...
#
# gives:
#
# .Release.Name = climbing-dev
#
# Therefore:
#
# name: {{ .Release.Name }}-climbing-management
#
# becomes:
#
# name: climbing-dev-climbing-management

USEFUL DEBUGGING FLOW
---------------------

# When a Helm deployment is not working:

# 1. Check the Helm release.

helm status climbing-dev


# 2. Check the release history.

helm history climbing-dev


# 3. Check the generated manifest.

helm get manifest climbing-dev


# 4. Check Kubernetes resources.

kubectl get pods

kubectl get deployment

kubectl get service


# 5. Check the Pod status.

kubectl describe pod <pod-name>


# 6. Check application logs.

kubectl logs deployment/climbing-dev-climbing-management


# 7. Check which Docker image is running.

kubectl get pod <pod-name> `
-o jsonpath="{.spec.containers[0].image}"


# 8. If necessary, check the actual image digest.

kubectl get pod <pod-name> `
-o jsonpath="{.status.containerStatuses[0].imageID}"


# 9. If the problem was introduced by a Helm upgrade,
#    consider rolling back.

helm rollback climbing-dev <revision>
